# CoreIntegrations 3.1.0: консолідація 3.0.x

Дата: 2026-10-13. Гілка: `rework/3.1.0` від `releases/3.0.4` (`c7e7596`).

## Мета

Звести 3.0.2–3.0.4 і фікси з відкритих PR galean/CoreIntegrations#13 і #14 в одну узгоджену модель, яка простіша за обидва джерела:

- одне правило потоків замість `MainQueueExecutor` + `generation` + `perform(in:)` + захисних переходів на main, які нічого не роблять;
- спроба конфігурації як об'єкт замість `reset()` спільного синглтона;
- ATT і AppsFlyer 7 без діагностичної інфраструктури 3.0.4;
- робочий потік no-internet для Китаю за продуктовою специфікацією 2024-12.

PR #12, #13, #14 у поточному вигляді цим замінюються. В origin нічого не публікується, поки зміни не переглянуто.

## Контекст

- 3.0.2 (`28c3234`): ATT-рефакторинг прибрав `attAnswered = false` з `reconfigure()`. Повтор після `.noInternet` з того часу ніколи не завершується: `attConcentGiven` і таймер для нової спроби ніхто не ставить.
- Китайський перезапуск після ATT (`b0cc394`, 2025-04) виконується на кожному запуску, а не лише на першому: подвійний `coreConfigurationFinished` і `framework_finished`.
- `AppConfigurationManager` змінюється з main, глобальної черги таймера і completion мереж без синхронізації: креш на старті (ClickUp 869fc51e4).
- `NetworkManager` пише стан і ітерує обробники на своїй черзі, а читається з main (869fc9rzh).
- `syncOnAppStart` не викликає completion для вже зареєстрованої інсталяції.
- AppsFlyer 7 більше не чекає ATT сам (`waitForATTUserAuthorization` прибрано), тому старт сесії мусить гейтити фреймворк.
- Продуктова специфікація no-internet (ClickUp 8698ya1qy, 8698y8q8b, 2024-12): Китай, перший запуск, обидва сервіси впали → помилка → застосунок може показати алерт (опційно) → при поверненні фреймворк повторює конфігурацію і завершує її за ~5–6 с незалежно від мережі; алерт не частіше разу на інсталяцію.

## 1. Потоки

- Увесь стан конфігурації (`CoreManager`, `ConfigurationAttempt`, `NetworkManager`, стан ATT, `AppfslyerManager`) змінюється лише на main.
- Фоновий код переходить на main рівно один раз, у completion зовнішнього SDK або запиту, через `MainQueueExecutor.perform`.
- Внутрішні точки входу перевіряють `assert(Thread.isMainThread)`; додаткових переходів на main немає.
- Таймери: `DispatchQueue.main.asyncAfter`.
- `NWPathMonitor` стартує на `.main`; монітор не скасовується (фікс 3.0.4 залишається).
- `@MainActor` на `PurchasesManager` і пов'язаних методах `CoreManager` залишається без змін.

## 2. Спроба конфігурації

`ConfigurationAttempt` замінює `AppConfigurationManager`:

```swift
final class ConfigurationAttempt {
    init(events: [any ConfigurationEvent],
         isFirstStart: Bool,
         timeout: Int,
         alreadyCompleted: [(event: any ConfigurationEvent, error: Error?)])

    var onAttAndConfigLoaded: (() -> Void)?
    var onAttributionFinished: (() -> Void)?
    var onFinished: ((ConfigurationResult) -> Void)?

    private(set) var isCancelled: Bool
    var isAttributionFinished: Bool { get }
    var completedWithNetworkErrors: Bool { get }   // model.checkCompletedWithErrors()
    var statusForAnalytics: [String: String] { get }

    func complete(_ event: any ConfigurationEvent, error: Error?)
    func startTimer()
    func cancel()
}
```

- Немає `shared`, `reset()`, `generation`, `waitingCallbacks`. Колбеки призначає `CoreManager` при створенні спроби; `signFor*()` зникають.
- Кожен асинхронний запит захоплює свою спробу і після переходу на main викликає `attempt.complete(...)`. Для скасованої спроби `complete`, таймер і колбеки нічого не роблять.
- Таймер належить спробі; таймер скасованої спроби не може завершити нову.
- Колбек `onAttributionFinished` може скасувати спробу (гілка no-internet). Після нього `checkConfiguration()` перевіряє `isCancelled` і зупиняється.
- `CoreConfigurationModel` залишається як є.

### Факти процесу

`CoreManager` зберігає те, що стається один раз на процес, і передає це кожній новій спробі через `alreadyCompleted`:

- відповідь ATT (`attConcentGiven` з помилкою таймауту, якщо була);
- події застосунку, позначені через публічний `ConfigurationEvent.markAsCompleted()`;
- успіх AppsFlyer conversion data, якщо вже прийшов (`appsflyerWeb2AppHandled` без помилки).

`ConfigurationEvent.markAsCompleted()` (публічний) переходить на main, записує факт процесу і позначає поточну спробу. `InternalConfigurationEvent.markAsCompleted(error:)` прибирається: внутрішній код викликає `attempt.complete` напряму.

Колбеки AppsFlyer (conversion success/failure) позначають поточну спробу, а не ту, в якій стартувала сесія: результат, що прийшов пізніше, зараховується повтору.

## 3. ATT

Поведінка:

- якщо `useDefaultATTRequest == true`, `requestATT()` на кожному `applicationDidBecomeActive`; якщо статус уже відомий, щоразу оновлюється user property `att_status`;
- відповідь фіксується один раз на процес з першого джерела: колбек `requestTrackingAuthorization`, опитування статусу кожні 0.5 с, fallback 5 с (`.notDetermined` + `NSError(domain: "coreintegrations.att.timeout", code: 6456)`), публічний `handleATTPermission(_:)` (`.notDetermined` звідти = таймаут);
- `att_permission` надсилається лише для відповіді, отриманої в цьому процесі (не для вже відомого статусу). Якщо активація бачить відповідь, поки наш запит ще в польоті, це відповідь цього процесу.
- Відповідь, отримана до `configureAll` (ранній `handleATTPermission`), зберігається і застосовується в кінці `configureAll`.

Реалізація в `CoreManager+ATT.swift`, без окремих типів:

```swift
var attAnswer: ATTAnswer?                 // status + optional error
private var isATTRequestInFlight = false

func requestATT()
private func pollATT(until deadline: Date)
private func resolveATT(_ status: ATTrackingManager.AuthorizationStatus, source: ATTSource)
func applyATTAnswer(_ answer: ATTAnswer)
```

`applyATTAnswer(_:)`: якщо Китай і перший запуск → секція 5; інакше `startConfigurationAttempt()` для поточної спроби (позначити `attConcentGiven`, запустити таймер, `framework_attribution_started`), далі `facebookManager?.configureATT`, `appsflyerManager?.handleATTResolved()`.

Видаляються: `ATTResolutionCoordinator`, `ATTResolutionPolicy`, `ATTResolutionCancellation`, `ATTResolutionPolicyExecutableTests`.

## 4. AppsFlyer

Залишається з 3.0.4: `initialize(devKey:appId:)`, `handleLaunchOptions`, `registerSessionReadyListener`, спостереження `didEnterBackground`, sharing filter перед `start()`, `setAdPartnersDataSharingEnabled`, перехід колбеків conversion data на main, збереження `deeplinkResult`.

Гейти старту в одному чистому типі:

```swift
struct AppsFlyerStartGate {
    var isATTResolved = false
    var isSessionReady = false
    private var didStartThisCycle = false

    mutating func enteredBackground()                          // isSessionReady = false; didStartThisCycle = false
    mutating func claimStart(hasCustomerUserID: Bool) -> Bool  // всі умови виконані і в цьому циклі ще не стартували
}
```

- Наявність user ID читається з SDK (`customerUserID != nil`) у момент перевірки, тож ID, який SDK уже має, теж враховується; сеттер `customerUserID` лише запускає перевірку. `startAppsflyer()` прибирається. Sentry-лог `coreintegrations.appsflyer.noCustomerUserID` у `CoreManager.applicationDidBecomeActive` залишається.
- `sessionStatus: String` — `not started` / `starting` / `started` / `error: <domain> <code>`, оновлюється в completion `start()`; `CoreManager` кладе його в статус під ключем `appsflyerSession`.

Видаляються: `AppsFlyerSessionTally`, `AppsFlyerSessionState`, `AppsFlyerStartAttempt`, `AppsFlyerSessionStartPolicy`, розпізнавання rate limit, прапорці `coreintegrations_appsflyer_didStartSuccessfully` / `didReportStartFailure`, Sentry `Appsflyer_session_start_error`, методи делегата `appsflyerSessionStartFailed` / `appsflyerSessionStartAttemptFailed`, подія `framework_appsflyer_start_failed`, `didDeliverConversionData`, `appsflyerSession`, `onAppOpenAttributionFailure`, `AppsFlyerMigrationExecutableTests`.

Відоме обмеження: повтор після `.noInternet`, запущений появою мережі в тому самому foreground-циклі, не стартує нову сесію AppsFlyer. На завершення спроби це не впливає (таймер), а conversion data, що прийде пізніше, зарахується поточній спробі.

## 5. Китай і no-internet

### Перший запуск у Китаї

Умова: `AppEnvironment.isChina && configuration.appSettings.isFirstLaunch`. На повторних запусках Китай іде звичайним шляхом.

1. Після відповіді ATT: `framework_start_delayed`.
2. Чекати, що станеться раніше: мережа доступна (`NetworkManager`) або 6 с. Обидва тригери на main, один прапорець.
3. Скасувати поточну спробу і створити нову (перша вже містить запити, що впали через системний діалог WLAN): факти процесу, перезавантаження remote config, `startConfigurationAttempt()`, `facebookManager?.configureATT`, `appsflyerManager?.handleATTResolved()`.

### `.noInternet` і повтор

Логіка рішень — чистий тип:

```swift
struct NoInternetRetry {
    private(set) var isOptedOut = false   // handleNoInternetAlertWasShown() до будь-якого .noInternet
    private var state: State = .idle     // idle → waiting → retried

    mutating func optOut()
    mutating func shouldDeliverNoInternet(isChina: Bool, isFirstLaunch: Bool,
                                          completedWithNetworkErrors: Bool) -> Bool  // true → state = waiting
    mutating func enteredBackground()
    mutating func claimRetry(for trigger: Trigger) -> Bool  // waiting → retried, рівно один раз; .activation лише після фону
}
```

1. У `onAttributionFinished`: якщо `shouldDeliverNoInternet(...)` → `attempt.cancel()`, `delegate.coreConfigurationFinished(.noInternet)`, підписка на `NetworkManager`. `framework_finished` для цієї спроби не надсилається (як зараз).
2. Тригери, хто перший викличе `claimRetry()`:
   - наступний `applicationDidBecomeActive` після переходу застосунку у фон (наприклад, у Settings), незалежно від мережі; активація після системного діалогу без виходу у фон повтор не запускає;
   - мережа доступна, коли `UIApplication.shared.applicationState == .active`; якщо вона доступна вже в момент підписки — повтор через `DispatchQueue.main.async`, щоб не стартувати вкладено у фініш попередньої спроби.
3. Повтор: нова спроба з фактами процесу → перезавантаження remote config → запит до сервера атрибуції (через `onAttAndConfigLoaded`) → `startConfigurationAttempt()` (таймер одразу). Завершується по подіях або по `configurationTimeout`, тобто `.finished` приходить завжди.
4. Другий провал: `shouldDeliverNoInternet` повертає `false` (стан `retried`) → `.finished` з помилками.

`handleNoInternetAlertWasShown()`: виклик до будь-якого `.noInternet` → `optOut()`: `.noInternet` не повертається, провал завершується як `.finished` з помилками, повтору немає (поведінка Scanner збережена). Виклик після `.noInternet` ні на що не впливає.

Оновлення атрибуції (`handlePossibleAttributionUpdate`) ігнорує скасовану спробу: вона зберігає прапорець завершеної атрибуції, а оновлення належить повтору.

`checkIsNoInternetError()` і читання спільних `remoteError` / `installError` прибираються: рішення приймається за `attempt.completedWithNetworkErrors`. Помилка `remoteConfigLoaded`/`remoteConfigUpdated` береться в completion запиту до переходу на main; якщо атрибуція не змінилась і запиту немає, `remoteConfigUpdated` позначається без помилки.

### `syncOnAppStart`

Для вже зареєстрованої інсталяції completion викликається завжди, асинхронно на main, зі збереженим `installResultData` (`nil` для старих даних без результату); перед цим `installError` обнуляється, бо запиту не було. `attributionServerHandled` отримує помилку лише при `result == nil`, і це помилка цього запиту, а не спільний `installError`.

## 6. Публічне API

Без змін сигнатур: `CoreManagerProtocol` (зокрема `handleATTPermission`, `handleNoInternetAlertWasShown`, `setAdPartnersDataSharingEnabled`, `@MainActor` методи), `CoreConfigurationProtocol.isAdPartnersDataSharingEnabled`, `ConfigurationEvent.markAsCompleted()`, `PurchasesManagerProtocol`.

Зміни поведінки (документуються в коді):

- `CoreManagerDelegate.coreConfigurationFinished(result:)` — на main (і в тестовому режимі `xctest_remote_config_enabled`); після `.noInternet` рівно один `.finished`.
- `CoreManagerDelegate.coreConfigurationUpdated()` — на main.
- `ConfigurationEvent.markAsCompleted()` — на main синхронно, з іншого потоку асинхронно.
- `CoreManagerProtocol.handleNoInternetAlertWasShown()` — лише opt-out.
- `AttributionServerManager.syncOnAppStart` — completion завжди (doc-коментар і в `AttributionServerManagerProtocol`).
- Doc-коментар вимоги `ConfigurationEvent.markAsCompleted()` у протоколі описує нову поведінку.

Видаляється (модуль `AppsflyerIntegration`): `AppfslyerManagerProtocol.appsflyerSession`, `.didDeliverConversionData`, `.startAppsflyer()`; `AppsflyerManagerDelegate.appsflyerSessionStartFailed(_:shouldReport:)`, `.appsflyerSessionStartAttemptFailed(_:attempt:)`; `AppsFlyerSessionState`, `AppsFlyerStartAttempt`; `AppfslyerManager.onAppOpenAttributionFailure(_:)`.

Додається: `AppfslyerManagerProtocol.sessionStatus: String`.

Аналітика: прибирається `framework_appsflyer_start_failed`; `framework_start_delayed` лише на першому запуску в Китаї; значення `appsflyerSession` змінюються (ключ той самий).

Версія 3.1.0: `CoreIntegrations.podspec`, `README.md`, `AttributionDataWorker.sdkVersion`.
